The hard part

20 customers, one slot, the same instant

Check R3.12 registers 20 customers, then fires all 20 booking requests at one slot in parallel. On PostgreSQL with a 10-connection pool these really do race.

1 · Atomic claim

Booking is one conditional update. The database lets exactly one request see "1 row updated"; every other request sees 0 and gets 409. There is no gap between check and write.

UPDATE time_slot
   SET status = 'BOOKED'
 WHERE id = :slotId
   AND status = 'AVAILABLE'

2 · Database backstop

Even if application code were wrong, the schema refuses a second active booking for the same slot. Cancelled rows stay for the audit trail.

CREATE UNIQUE INDEX
  ux_one_active_booking
  ON appointment (slot_id)
  WHERE status = 'BOOKED';

3 · All-or-nothing cancel

The appointment update and the slot release share one transaction. If the release fails, the cancellation is rolled back. A test forces that failure to prove it.

// one @Transactional method
appt.cancel(reason, now);
int n = releaseSlot(slotId);
if (n == 0) throw conflict();
// throwing rolls back both
Domain model

Slot lifecycle

Only AVAILABLE slots appear in search or can be booked. Every transition is a conditional update, so an illegal or racing transition changes nothing and returns 409.

web4 controllers, validated request records, paging parameters. No business logic.
serviceBusiness rules and transaction boundaries. An injected clock makes time-based rules testable.
repositorySpring Data JPA, criteria-based search, the atomic conditional updates, row locks.
databaseExplicit SQL schema with CHECK constraints, foreign keys, search indexes and the one-active-booking index.
Backtest

Gaps found and fixed

Before the review, each line of the brief was turned into testable statements. Five gaps turned up. Each one now has code and a test.

Brief saysGap foundFix
"define and manage their time slots"Only create, lock and unlock existedReschedule (PUT) and delete (DELETE) for slots never booked; slots with history must be locked instead
"400 for invalid time ranges"Booking with end before start returned 404Now 400 INVALID_TIME_RANGE
"within an atomic transaction"Atomic in code, but not provenTest breaks the slot release mid-cancel and checks nothing was saved
"robust consideration"One customer firing two overlapping bookings at once could get both on PostgreSQLCustomer row locked during booking; race test added
"validate slot non-overlap"No test for simultaneous overlapping creates10 overlapping creates at once: exactly 1 slot saved

Reproduce

Run it yourself

Needs Java 21 and Maven. The check script needs only bash and curl.

mvn spring-boot:runStarts on port 8080 with demo data. Swagger UI at /swagger-ui.html
./acceptance-check.sh56 PASS/FAIL checks, grouped R1 to R5, against the running server
mvn test -Dtest.profiles=test,postgres,pgtestThe 24 integration tests on PostgreSQL (plain mvn test uses SQLite)
Known limitations: no login (the customer ID is sent in the request); searching with an unknown provider ID returns an empty page rather than 404; booking by time range needs an exact slot match. Full details are in docs/BACKTEST_REPORT.md and docs/DESIGN.md in the repository.
